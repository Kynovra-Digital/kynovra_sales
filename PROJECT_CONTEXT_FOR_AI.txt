KYNOVRA SALES - CONTEXTO COMPLETO PARA OUTRA IA
Atualizado em: 2026-06-26

Resumo rapido
=============
Kynovra Sales e um SaaS interno/proprietario da Kynovra Digital para vendas, atendimento comercial, suporte pos-venda, campanhas, produtos, estoque, leads, permisssoes, auditoria, notificacoes e IA em tempo real.

Arquitetura final aprovada:
- Next.js = somente frontend/interface/rotas visuais/componentes/UX.
- Supabase = todo backend: PostgreSQL, Auth, RLS, RPC, Edge Functions, Realtime, Storage, policies, auditoria e regras de negocio.
- Frontend nunca chama LLM direto.
- Frontend nunca usa service_role.
- Frontend nunca cria backend local em app/api.
- Frontend consome Supabase por supabase.from, supabase.rpc, supabase.functions.invoke, supabase.channel e supabase.storage.
- Dados reais devem vir do Supabase. Mocks nao devem alimentar telas finais.

Regras criticas do projeto
==========================

- Next.js e interface.
- Supabase e backend completo.

Auth e verificacao de conta
===========================
- Login real via Supabase Auth.
- app/(auth)/login/page.tsx usa supabase.auth.signInWithPassword.
- Se Supabase retornar erro de e-mail nao confirmado, a tela mostra estado de verificacao pendente e botao para reenviar verificacao.
- Reenvio usa supabase.auth.resend({ type: "signup", email, options.emailRedirectTo }).
- Callback criado em app/(auth)/auth/callback/route.ts.
- Callback valida token_hash/type com supabase.auth.verifyOtp e redireciona para /dashboard.
- supabase/config.toml local esta ajustado para enable_confirmations = true.
- SMTP local configurado para Resend via SUPABASE_AUTH_SMTP_PASS.
- Em producao, confirmar no painel Supabase: Email Confirmations ligado, SMTP configurado, redirect URL /auth/callback permitido.

Supabase Auth SMTP
==================
Config local em supabase/config.toml:
- [auth.email] enable_confirmations = true.
- [auth.email.smtp]
  - enabled = true
  - host = smtp.resend.com
  - port = 587
  - user = resend
  - pass = env(SUPABASE_AUTH_SMTP_PASS)
  - admin_email = onboarding@resend.dev
  - sender_name = Kynovra Sales

Nao salvar chaves no repositorio.

Atendimento de venda
====================
Rotas:
- Publica entrada: /a/[productSlug]
- Sala publica: /room/[publicToken]
- Admin: /sales

Fluxo correto aprovado:
1. Cliente acessa link do produto.
2. Cliente informa nome/e-mail.
3. Backend cria ou recupera sessao por visitor_id se ainda valida.
4. Cliente vai para /room/[publicToken].
5. Cliente fica em loader.
6. Chat nao aparece enquanto status waiting/waiting_for_acceptance e accepted_by null.
7. Ticket aparece na fila interna.
8. Atendente aceita via RPC.
9. Ticket some dos outros.
10. Ticket fica em meus atendimentos.
11. Atendente abre atendimento.
12. Chat publico aparece apenas quando status vira in_progress/ai_takeover ou accepted_by valido.
13. Se timeout passar e ninguem aceitar, IA assume.
14. IA responde automaticamente enquanto cliente responde.

Estados:
- waiting_for_acceptance
- waiting
- accepted
- in_progress
- transferred
- closed
- ai_takeover

Campos importantes:
- accepted_by
- accepted_at
- opened_at
- closed_at
- handled_by_type = human | ai
- ai_takeover_at
- public_token
- visitor_id
- visitor_expires_at

Visitor identity:
- Ao acessar o link, backend cria visitor_id aleatorio e cookie seguro.
- Dados anonimos ficam no banco ligados a visitor_id.
- Se o cliente volta no mesmo link/produto no prazo de 1 dia, deve recuperar a mesma sessao e conversa.
- visitor_id expira por tempo ou quando atendimento e encerrado.
- Se humano atendeu antes e ainda nao encerrou, sessao continua com humano/meus atendimentos.
- Se transferir para IA, atendente sai e IA assume.

Checkout:
- Card "Checkout Gerado" na tela do cliente so deve aparecer quando atendente enviar/acionar checkout.
- Nao deve aparecer automaticamente.

Encerramento/feedback:
- Quando IA ou humano encerra, cliente ve mensagem de agradecimento + avaliacao.
- Feedback com perguntas e 1 a 5 estrelas.
- Ao avaliar, mostrar "Atendimento encerrado, obrigado por entrar em contato."
- Encerrar expira visitor_id.

Como orientar outra IA
======================
Se outra IA for trabalhar neste projeto, ela deve seguir estas prioridades:
1. Ler este arquivo e AGENTS.md local se existir.
2. Preservar arquitetura: Next frontend, Supabase backend.
3. Nao criar app/api.
4. Nao usar mocks como solucao final.
5. Nao expor secrets.
6. Sempre verificar schema/RLS/RPC antes de alterar frontend.
7. Usar queries finas em lib/supabase/queries.
8. Usar TanStack Query para dados reais.
9. Usar Supabase Edge Functions para IA/e-mail/logica protegida.
10. Rodar pnpm check, pnpm lint, pnpm test:run e build antes de finalizar.

Estado final esperado do produto
================================
Kynovra Sales deve ser um SaaS Command Center premium para operar vendas e suporte com humanos + IA:
- Produto cria link publico.
- Cliente entra, informa dados e espera no loader.
- Atendente aceita ou IA assume por timeout.
- Chat abre somente depois disso.
- IA atua como copiloto para sugerir respostas baseadas no contexto real.
- Suporte tem link unico global.
- Produtos, campanhas, base de conhecimento, equipe e configuracoes usam Supabase.
- Hardness define os templates de prompt dos agentes por produto.
- Tudo em tempo real, com RLS, auditoria, permissoes e storage.
